title: "Get working hours"
description: "Read the regular weekly working hours for a business."
api: "GET http://ext-integration.haat-delivery.io/api/pos/business/{businessId}/working-hours"
---

Read-only. Returns the business's **regular weekly** working hours. Use after PUT to confirm what HAAT stored, or to load the schedule into a POS UI.

Does **not** include occasion overrides, temporary special hours, or days off.

Does **not** return a `requestId` and does not create a sync audit entry. For writes, use [Update working hours](/kits/advanced-api/working-hours).

GET uses the same `days` / `day` / `hours` / `type` / `fromHour` / `toHour` shape and the same UTC `HH:mm` convention as PUT.

### `type` values

| `type` | Meaning on GET |
| --- | --- |
| `0` | Open with specific hours (`hours` has one or more ranges) |
| `1` | Closed — **never returned**; the day is omitted instead |
| `2` | Open 24 hours (`hours` is `[]`) |

### UTC and DST

Same convention as PUT: `HH:mm` UTC. After a successful PUT, GET returns the same UTC values while the country's UTC offset is unchanged. Operator UIs may show **local** time (offset from these UTC values).

If the country UTC offset changes (for example daylight saving) and hours are **not** rewritten, GET's UTC `HH:mm` values **may shift** so local opening times stay consistent. Do not assume UTC clock strings never change after DST without another PUT (or equivalent hours update in HAAT).

### Relation to PUT

- Same schedule fields and the same numeric `type` values `0` / `1` / `2`
- GET = read schedule; PUT = full-replace write + sync response
- On PUT, any day left out of the request is treated as closed (do **not** send `type: 1`)
- Partners may round-trip GET `days` into a PUT body after edits; PUT remains full replacement
