# Group 2 — The POS only tells us availability, price, or text

No menu creation. These assume the menu already exists in Haat and is already mapped.

## EasySolution (restaurants)

- **Who starts it:** **We do.** A scheduled background job calls their HTTP API to fetch the menu.
- **Transport:** HTTP GET.
- **What it changes:** Only **hide/show** flags and **translations** on items we already mapped. It will not create new meals.
- **Matching key:** `PosId`.

## BeecommCloud and LeenCopot (restaurants)

- **Who starts it:** **We do**, as part of keeping POS menu history fresh.
- **Transport:** HTTP GET.
- **What it changes:** Nothing in the Haat menu directly. It refreshes our stored copy of *their* item list plus availability, which supports mapping and ordering.
- **Matching key:** `PosId`.

## Generic POS API — used by any POS we onboard (restaurants)

This is the modern, reusable path at `/api/pos/business/{businessId}/...`, with a token per POS.

- **Who starts it:** The POS does.
- **What they can do:** open/close the branch (`PUT /status`), start-prepare or cancel an order (`PUT /order-status`), update working hours (`PUT /working-hours`), and mark items available/unavailable (`PUT /availability`).
- **What it changes:** Availability and operational state only — **no menu creation**.
- **Matching key:** `PosId` in the availability call.

<Tip>
  **For PMs:** point new POS vendors at the [Advanced API kit](/kits/advanced-api/overview). It's generic, so we don't write a new integration per vendor.
</Tip>
